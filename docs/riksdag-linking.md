# Linking promises to Riksdag documents: the pipeline

Epic `hemsida-4np`. This is the map of how a promise gets its Riksdag evidence, which tool does each step, and where each artifact lives. The details are in the linked docs; this page exists so the whole flow is in one place.

**Principle:** tools find and rank candidates, the judge (step 7) labels pairs, and Claude writes `evidence[]` and sets verdicts with written reasoning (`docs/data-model.md`). There is no human review step. Steps 1 to 7c produce no verdict; step 8 does. The SFS steps (7b, 7c) are how a promise can become `fulfilled` or `partially_fulfilled`: the Riksdag steps find the proposition, the SFS register finds the law it produced.

## The SFS step end to end (7b, 7c, 8)

`data.riksdagen.se` cannot link a proposition to the law it produced, so laws come from Regeringskansliets SFS register (`docs/riksdag-api.md`, "SFS register"). The chain, run per term after the Riksdag evidence is in place:

1. **Ingest** (`node --experimental-strip-types tools/ingest-sfs.ts [--term T] [--dry-run] [--refresh]`): searches the register for every non-budget, non-skrivelse proposition in the riksdag store, fetches each hit once (1 request/s, raw pages cached in `tools/out/sfsr-cache/`) and keeps the base acts and amendments whose Förarbeten cite exactly that proposition. Output `tools/out/sfs-store/<term>.json`. Free, but a first run takes a while because of the 1 request/s limit; reruns only fetch what is missing.
2. **Judge** (`node --experimental-strip-types tools/judge-sfs.ts [--name <run>] [--id-prefix tido-] [--dry-run]`): for each legislative promise and each law reached through a proposition already linked as evidence, the model labels coverage `full`, `partial`, `weaker` or `none` with confidence, Swedish `covered_sv` / `missing_sv` and an English reason. It runs through the local Claude Code subscription login (no API key; `--judge fake` for offline tests) and caches by judge kind, model, template version (now `v3`) and prompt. `--max-cost` (default 15 USD) is an overall cap per run name: spend accumulates in `manifest.json` and is subtracted on resume. Do a `--dry-run` first; it shows the pair count and a cost estimate. Output `tools/out/sfs-judge-runs/<name>/results.json`.
3. **Apply** (`apply-links.ts --run <link-run> --id-prefix tido- --sfs-store tools/out/sfs-store/<term>.json --sfs-run <name> --sfs-overrides tools/sfs-overrides.json [--today YYYY-MM-DD] [--dry-run]`): adds `sfs` evidence and sets the verdict by the rules in "Evidence and verdicts" below and in `docs/data-model.md`. Then `pnpm fmt`.
4. **Reasoning** (`write-reasoning.ts`, below): replaces the mechanical placeholder text with plain Swedish. Verdict-aware: for promises with an sfs item the prompt explains what `fulfilled` and `partially_fulfilled` mean, and the validator rejects claims that a law is in force unless an sfs item with an in-force date up to today exists.

Cost: ingest is free; the judge is the only paid step (it runs on subscription usage, not API billing; the dry run prints an estimate and `--max-cost` bounds it, and a rerun with the same template is free from the cache); `apply-links` is offline and `write-reasoning` is one short model call per changed promise.

Caveats:

- The register has no API. Ingest reads HTML pages, so a change in Regeringskansliets markup breaks the parsers (they throw on a page they cannot classify rather than guess; fixtures in `tools/lib/sfs-register.fixtures.ts`). The register is also only as current as its owner's updates: a law enacted recently may be missing until the register catches up; rerun with `--refresh`, which only refetches propositions that had no law in the previous store. A new amendment to a proposition that already has a law needs the cached register pages for it deleted from `tools/out/sfsr-cache/` first.
- Some entries have no in-force date (`ikraft` is null). They are not added as evidence (the schema needs a date). An undated law blocks `fulfilled` on its proposition, and a proposition whose only laws are undated counts as pending, so the promise stays `in_progress`.
- The judge is not fully reliable, mostly in the `full` direction. Earlier templates called `full` too readily for laws that only share a proposition with the real measure; v3 asks what this specific law does and treats a consequential amendment or a measure that sits in another law of the bill as `none`. Even so, known wrong fulls are corrected by hand in `tools/sfs-overrides.json` (`"<promise>::<sfs-key>"` with a replacement label and a reason; applied before any rule, so a corrected pair is visible in one place and reviewable in a PR). Add an entry when review finds a wrong label; do not edit promise files by hand. A `full` below high confidence never gives `fulfilled`; alone it leaves the promise `in_progress`.
- Carry-over can hide fulls. `--pairs-from <results.json> --labels full,partial` re-judges only the pairs the earlier run called `full` or `partial` (plus never-judged pairs) and keeps earlier `none` and `weaker` labels, on the assumption that a stricter prompt only moves labels towards `none`. That is not exact: some pairs do move from `partial` to `full` with a newer template (5 pairs in the v1 to v2 pass, 6 between v1 and the final mixed v1/v2/v3 results), so a carried-over `none` or `weaker` label may in rare cases be one the newer template would have raised. After a template change that loosens anything, or when a verdict looks too low, rerun without `--pairs-from` for the promises concerned (`--only <id>` or `--ids`) under a NEW `--name` (the already-judged pairs come from the judge cache). Reusing a name overwrites its `results.json` with only the filtered pairs, and `apply-links` reads exactly one `--sfs-run`, so it would then drop sfs entries and move AI `fulfilled` / `partially_fulfilled` verdicts back to `in_progress`. To combine runs, rerun the whole set under the new name.
- Only `legislative` promises and laws reached through already linked propositions are considered. A law that never passed through a linked proposition (for example an ordinance or a law linked by no proposition) is not found.

## Evidence and verdicts (step 8)

`node --experimental-strip-types tools/apply-links.ts --run <link-run> --id-prefix tido- [--dry-run]` (rules in `tools/lib/apply-links.ts`, tested) reads a judged link run and, for each promise still `unassessed` without Riksdag evidence, adds the pairs the judge proposed as `evidence[]` (one entry per document; `match` is `full`, `partial` is `partial`) and sets the verdict:

- `in_progress` when the evidence includes a dir, sou, ds or prop, with Swedish reasoning that lists the documents, and `assessedBy: "ai"` (the site shows the AI tag; the reasoning carries no disclaimer);
- otherwise the promise stays `unassessed` (a betänkande alone may only reject motions).

Skrivelser (the store files them under `prop`) and pairs the judge staged as `background` are not used as evidence. It never sets `no_evidence` (needs an exhaustive search) or `broken` (`contradicts` labels are reported, not applied); `fulfilled` and `partially_fulfilled` need SFS input (below). Eligible promises are `unassessed` ones (Riksdag evidence already there stays and new documents are merged in by `dok_id`; one that already has a dir, sou, ds or prop is treated as curated and skipped) and ones tagged `assessedBy: "ai"`, which are recomputed from the newest judgements: their Riksdag evidence is replaced, the earlier verdict goes to `history` when its value changes, and a promise with no proposed planning document left falls back to `unassessed`. Any other verdict is left alone. A rerun that changes nothing writes nothing. Run `pnpm fmt` afterwards.

**SFS evidence and the law-backed verdicts.** With `--sfs-store tools/out/sfs-store/<term>.json --sfs-run <name | results.json path> [--sfs-overrides tools/sfs-overrides.json]` (both flags together; without them nothing below happens) `apply-links` also handles `legislative` promises only, and only the laws reached through propositions that are already evidence on the promise (`byProp`; budget propositions and skrivelser excluded). Each law the SFS judge (`docs/riksdag-linking.md`, "SFS coverage judge") labelled `full`, `partial` or `weaker` becomes an `sfs` evidence entry (`dok_id` `sfs-YYYY-N`, designation `SFS YYYY:N`, title from the register, `date` = in-force date, relevance `full` for `full`, otherwise `partial` with the judge's `missing_sv` as note). A law with no judgement, label `none` or no in-force date is not added. A law is in force when its in-force date is on or before `--today`, which is also the verdict date:

- no law in force: `in_progress` (the placeholder reasoning names the in-force date of a future law);
- pending work also keeps `in_progress`: another linked proposition with no law in force (any law, whatever the judge made of it), or a linked dir, sou or ds dated after the newest proposition that has a law in force;
- `fulfilled`: a law judged `full` at `high` confidence is in force, no linked law is judged `weaker`, and every linked judged law is in force (a future or undated law on the same proposition blocks it);
- `partially_fulfilled`: laws are in force, nothing is pending and either a high-confidence `full` is blocked as above or a law is `partial`/`weaker`;
- a `full` below `high` confidence alone is unconfirmed: `in_progress` with the sfs entry attached (medium fulls need confirmation).

The judge's lone `full` is not fully reliable, so `tools/sfs-overrides.json` (`"<promise>::<sfs-key>": {label, reason}`) replaces the judge label for a pair before any rule runs (seeded with three known wrong fulls; the laws that really do the work keep their judged labels). Without SFS input, ai `fulfilled` / `partially_fulfilled` verdicts are left untouched instead of being recomputed; a rerun with SFS input drops sfs entries the judge no longer supports and moves the earlier verdict to `history` when the value changes. Hand-set verdicts are never touched. The placeholder reasoning names the laws, their in-force dates and, for partial, what is missing; `write-reasoning` replaces it.

A `contradicts` judgement (stage not `background`, at the run's minimum confidence; `apply-links` applies the threshold itself because `proposed` in `results.json` only covers `accept_labels`) is written as evidence with relevance `contradicts` ("Motverkar" on the site). It never counts toward the verdict, never sets `broken` and never pulls in a deciding betänkande; a promise whose only evidence works against it stays `unassessed`. Reruns are idempotent.

The reasoning `apply-links` writes is a mechanical placeholder that lists designations. `node --experimental-strip-types tools/write-reasoning.ts --run <link-run> --id-prefix tido- [--only <promise-id>] [--model claude-sonnet-5-5] [--dry-run] [--limit n]` replaces it with two or three plain-Swedish sentences (what happened in time order, what the documents cover and what is missing) written from each document's type, date, title, coverage and the judge's note. It never names designations, because the evidence timeline beside the reasoning lists the documents, and it adds no AI or "more documents may exist" caveats (the site shows the AI tag, and ingestion status is stated elsewhere). Output is cached in `tools/out/reasoning-cache` by model, prompt version and evidence, so a rerun only writes promises whose evidence changed (a promise with a `contradicts` document gets extra instructions, so only those promises' cache keys differ); text that breaks the rules is rejected and retried, and a cached text that fails a stricter later validator is written again. The writer only sees the documents linked to the promise, so it may not claim that something was not decided, not proposed or is still pending (the validator rejects such phrasing, SFS designations, and claims that a law is or became in force unless an sfs evidence item with an in-force date up to today is present); promises with verdict `in_progress`, `fulfilled` or `partially_fulfilled` are processed, and the instructions describe the verdict meaning only when an sfs item is involved (the plain `in_progress` prompt is unchanged, so its cache stays valid); a sentence about the listed documents may say they show a proposal and no decision.

## Why scoring exists (step 5)

Keyword matching (step 2) caps at 15 candidates per promise, loses on vocabulary mismatch and snippet-only text, and nothing measured what it missed. The scoring harness asks every document a yes/no question per promise ("does the document describe or carry out something belonging to this promise?"), takes the highest chunk score per document, and is judged against the hand-labelled pairs (step 4): AUC, precision and recall at thresholds, and the rank of each pair's own promise among all 274. The score says a document is about a promise, not whether it fulfils it, which stage it is, or that it decided anything; those need the stage axis and a second-stage reader.

How a run works (plan, content-addressed cache, budget guard, config fields): `docs/scoring-harness.md`.

### Scorer results on the 51 eval pairs (same config, 535 requests, 274 questions each)

Jev numbers: `docs/jev-spike.md`. Haiku numbers were measured on 2026-11-08 in the `hemsida-aah` spike (run manifest and report in `tools/out/runs/haiku-experiment-v1/`, not committed; the results are also kept in the `claude-scorer-spike` beads memory). Rerun `pnpm score tools/score-configs/haiku-eval-v1.json` to reproduce them.

| Scorer                                                                  | AUC   | At threshold 0.5 (tp / fp / fn / tn) | At 0.7          | Cost and time                                                                           |
| ----------------------------------------------------------------------- | ----- | ------------------------------------ | --------------- | --------------------------------------------------------------------------------------- |
| `jev` (TypeSafe System One)                                             | 0.966 | 30 / 3 / 3 / 15                      | 26 / 0 / 7 / 18 | $0.99 for the 274-question run ($0.43 with 50 questions), minutes (`docs/jev-spike.md`) |
| `claude`, model `haiku` (5.5), Agent SDK on a Claude subscription login | 0.946 | 30 / 3 / 3 / 15                      | 25 / 2 / 8 / 16 | no money billed; about 90 minutes at concurrency 4; roughly $10 in list-price terms     |

Findings worth keeping:

- Haiku is competitive with Jev at the usual thresholds and slightly worse at the strict end. Jev is about 10x cheaper than Haiku's list-price equivalent and far faster, so it stays the default (and the only scorer in CI).
- `thinking: { type: 'disabled' }` had no effect through the Agent SDK (nor did `maxThinkingTokens: 0`, `effort: 'low'` or the `MAX_THINKING_TOKENS=0` environment variable in a small probe): every full request still spent roughly 2,000 to 11,000 thinking tokens and 8,000 to 18,000 output tokens. No zero-thinking Haiku run exists, so whether the score depends on thinking is unmeasured.
- `usage.input_tokens` from the Agent SDK is near zero once prompt caching applies; the scorer sums `modelUsage` (input, output, cache read, cache write) instead.
- Promise ids can be longer than the 64 characters Anthropic allows for tool-schema property names (one is 65), so the Claude scorer asks with positional keys (`q0`, `q1`, ...) and maps back.
- The real limit for a subscription-billed scorer is the account's rate-limit window, not money, and local concurrency does not raise it. A whole-corpus run (3,547 documents, roughly 37,000 requests by scaling from the eval set; an upper-end guess, the eval documents are longer than average) would take days on one login; several people each scoring a slice and sharing `score-cache` deltas is the way to parallelise.
- Whole-corpus scoring with Jev is projected at about $27 for the 274 Tidö promises and about $135 for all 1,468 promises (`docs/jev-spike.md`, unmeasured).

### Linking scores to candidates (step 5b)

`node --experimental-strip-types tools/link-scores.ts --run <name> [--threshold 0.55] [--top-k 10] [--dry-run]` reads a finished run's `results.json` and the ingest store (document metadata) and, per promise, appends up to `--top-k` documents scoring at least `--threshold` to the promise's candidate file. The defaults come from the eval report (0.5 to 0.6 gave 30 of 33 positives with 3 of 18 false positives). Added entries carry `found_by: ["score:<name>"]`, `score: 1` and a `relevance` field (the 0..1 score). Existing keyword entries stay as they are; if the run scored them they gain `relevance` and the `score:<name>` label. Pairs in `rejected-candidates.json` are skipped, and re-running with the same run changes nothing. The 15-per-promise cap of the keyword files does not apply to score hits. An incomplete run is refused unless `--allow-incomplete`.

It prints a recall summary and writes `tools/out/runs/<name>/link-report.json`: how many high-scoring pairs the keyword files already contain and how many they miss (the recall gain, per promise in the report), and how many keyword candidates score below the threshold (likely keyword noise). Candidate files change in a normal data PR. The matcher (step 7) reads them with `relevance` as a ranking signal.

## Where things live

- Committed: promises and evidence (`src/data/<term>/promises/`), candidates (`riksdag-candidates/`), rejected pairs (`rejected-candidates.json`), the eval set (`eval/pairs.json`), scoring configs (`tools/score-configs/`), freshness (`src/data/freshness.json`).
- Gitignored under `tools/out/`: the store, the full-text cache, the score cache and run manifests, evidence briefs, tier-1 extracts. Two of them are shared as release archives: `docs/cache-sharing.md`.
- Schemas: promise and evidence in `src/schema/promise.ts`, eval in `src/schema/eval.ts`, rejected pairs in `src/schema/rejected.ts`, scoring config in `tools/lib/score/config.ts`, cache manifest in `tools/lib/cache-archive.ts`.

The policy behind step 8 (when a verdict may be `in_progress`, `fulfilled`, `partially_fulfilled` or `broken`, how compound promises are split, and how documents that work against a promise are shown) is in `docs/data-model.md`, "Rules for setting a verdict from evidence".

### Splitting compound promises

A promise that bundles separate commitments is split with `tools/split-promises.ts --plan tools/split-plans/<plan>.json` (rule: `docs/data-model.md`, "Compound promises"). The plan lists, per parent, the parts with title, description, page and verbatim quote from the agreement text; the tool replaces the parent by one unassessed promise per part (a part whose slug starts with `utred` becomes an `inquiry`), copies the parent's candidates, points links from manifesto promises and candidates at all parts, and redirects the old page URL to the first part (`src/data/promise-redirects.json`, read by `astro.config.mjs`). Then link again: a link config with `inputs.promises.ids` set to the part ids (`tools/link-configs/link-tido-split-sonnet-v1.json`), `apply-links --run <that run>`, and `write-reasoning --run <main run>,<split run>` so the other promises keep their cached texts. The promises that were checked and kept as one are listed in `docs/tido-split-review.md`.

### SFS coverage judge (`tools/judge-sfs.ts`)

Linking a proposition to its laws is deterministic (`ingest-sfs.ts`, see `riksdag-api.md`); the judge only labels how much of a promise a law delivers: `full`, `partial`, `weaker` or `none`. Pairs are legislative promises times the laws reached through propositions already linked as evidence (budget propositions are skipped). The prompt asks for what this specific law does (register Rubrik and Omfattning); the proposition text is context, and a law that is only a consequential amendment, or whose measure sits in another law of the bill, is `none`. The judge sets no verdict; `apply-links` aggregates per promise.

- Cache: `tools/out/sfs-judge-cache`, key = judge kind, model, template version, instructions and prompt text (a `fake` run never fills real keys). Runs: `tools/out/sfs-judge-runs/<name>/results.json` (each result carries its `template_version`) and `manifest.json`.
- `--max-cost` is an overall cap for a run name: cumulative spend is recorded in `manifest.json` (`cumulative_cost_usd`) and subtracted on every resume; the CLI header shows the cap and what is already spent.
- `--pairs-from <results.json> --labels full,partial` re-judges, with the current template, only the pairs the earlier run labelled `full` or `partial` plus pairs it never judged. Pairs it labelled `none` or `weaker` keep their earlier label (and template version) because a stricter prompt only moves labels towards `none`. The earlier `results.json` is the input and is not modified.
